# Terac: live docs vs SPEC.md

Checked 2026-10-24 against `https://terac.com/docs/developers/openapi.json` (v2.0.0, base `https://terac.com/api/external/v2`) and the guides: authentication, webhooks, errors, filters, screening-questions, plus the researcher pages mcp, external-surveys, recruitment/filters and finance/pricing. The OpenAPI is the source of truth. No API key yet, so nothing here was called live. Everything below is tested with mocks in `tests/terac/**`.

## Resolved uncertainties (SPEC §20)

- **#2 casing.** Feasibility is camelCase (`taskDescription`, `panelDescription`, `submissionCount`, `timelineHours`, `costPerParticipant`). Everything else is snake_case (`num_participants`, `feasibility_request_id`, `submission_stats`, `rejection_category`, `target_url`, `event_types`). `src/lib/terac.ts` sends each shape as documented.
- **#3 webhook signature.** `X-Terac-Request-Signature` = `base64(HMAC-SHA256(secret, X-Terac-Request-Timestamp + rawBody))`, with no separator. The timestamp is in Unix seconds. The docs reject deliveries more than 300 s old, and so do we, in both directions. Deliveries also carry `X-Event-ID` (stable across retries; we dedupe on it) and `X-Timestamp` (ISO time of the event). The confirmation ping uses the same signature and has `event_type: "webhook.ping"`. Its full payload shape is not documented, so we accept `event_type` or `type`.
- **#8 sandbox.** This is confirmed: a sandbox is a separate org that Terac creates on request, and there is no self-serve signup. It has its own API key, webhook subscription and secret. `POST /opportunities/{id}/test-submissions {screening_outcome?, task_completion?: "automatic"|"redirect"}` returns 403 outside a sandbox, 409 if the opportunity is not active and 422 if the outcome is impossible. With `redirect`, the response includes a `task_url` with the IDs filled in, so our juror page plus callback can be tested end to end.

## Differences from SPEC §11.2 (code follows the docs)

| Topic | SPEC said | Docs say / what we do |
|---|---|---|
| Task type | `task_type: 'activity'` | `activity` **throws the work away** (it records only a button press). A task with its own page is `task_type: "interview"`, and that type requires `task_url`. We send `interview`. |
| Review type | `manual_review` | Confirmed. It is only settable via the API. A `completed` callback moves the submission to `awaiting_review` and never pays. Editing the task in Terac's dashboard builder silently replaces `manual_review`, so **never edit our tasks in the dashboard**. |
| `expected_days_to_complete` | `1` | The minimum is **5** (default 7). We send 5. Our own deadline/reconciler still governs refunds. |
| Task URL placeholder | `?sid={TERAC_SUBMISSION_ID}` | `{TERAC_SUBMISSION_ID}` is a documented placeholder. Terac also appends `teracSubmissionId`, `submissionId` and `taskId` itself. We keep `?sid={TERAC_SUBMISSION_ID}` (contract), and the page accepts all three names. An unsubstituted `{…}` value is treated as missing. |
| Filters | `filters` with slugs/options | The format is an array of single-key objects with Mongo-style operators: `{ "multi_select--country": { "$in": ["US"] } }`, `{ "integer--age": { "$gte": 25, "$lte": 45 } }`. Our `JurorProfile.filters` `{slug, options}` maps to `$in`, or to `$gte`/`$lte` for `integer--*` (options = `[min, max]`). Unknown slugs return 400. |
| No filters | (not mentioned) | A create with **neither `filters` nor `unrestricted_audience: true` is rejected**. With no filters we send `unrestricted_audience: true` (base audience is US, 18+, any language). |
| Screening questions | `screening_questions:[...]` | Each item is `{key, text, pick:"one"|"any"|"boolean"|"text"|"grid", answers:[{text, qualify_logic:"may"|"must"|"must_one_of"|"reject"|"review"}]}`. On `pick:"one"`, may/must collapse, so only `reject` screens anyone out. We map accepted options to `may` and the others to `reject`. |
| Launching with no screener | (not mentioned) | Returns 412 unless Terac has enabled it for the org **and** `without_screener: true` is sent. This is exposed as `launchOpportunity(id, { withoutScreener: true })`. Researchers should always provide ≥1 screening question. |
| Launch 412 reasons | balance/screener/$5/quote | Confirmed. A 409 means the opportunity is not a draft. The OpenAPI lists no 412 response for launch, but the description and errors guide do. |
| Opportunity pricing | `pricing.total_cost_cents`, `funding.affordable` | Confirmed, but `pricing` is **nullable**. `createOpportunity` throws `TeracError{code:"UNPRICED"}` rather than return $0, which would pass margin checks. `funding` also has `draws_on_credit`, `balance_cents` and `shortfall_cents`. |
| Charging | — | This is contradictory: the launch docs say launch "charges your organization's balance" (incentive × N + fee, unused budget refunded at stop/complete), but the pricing page says "credits are only deducted when you approve". Treat launch as a charge (the conservative choice) when checking balance. |
| Quote endpoint | `/feasibility/requests` | Confirmed. The pricing page mentions `POST /v2/quotes`, but **that endpoint does not exist in the OpenAPI**; we use `/feasibility/requests`. Statuses: `RECEIVED` → `RESPONDED` (priced), then `WON` (used at launch); `LOST`/`NOT_PURSUED` are terminal. The OpenAPI says pricing is "automatic within seconds or routed to a person", while the MCP page says "typically within about an hour". The 90-min QUOTING timeout is tight for niche panels. We also send `payRateFrequency: "ONE_TIME"`. |
| Feasibility once priced | — | A confirmed CPI only covers the brief that was priced. Filters and screeners added later are not part of it. |
| Stop | `POST /opportunities/{id}/stop {reason}` | Confirmed (`reason` ≤ 5000 chars). **Submissions still `awaiting_review` block the stop**: decide them first. Only `active`/`paused`/`pre_recruiting` can be stopped (409 otherwise); delete a draft instead. |
| Approve / reject | approve `{}`, reject `{rejection_category, rejection_reason}` | Confirmed. Both return 409 unless the submission is `awaiting_review`. Category and reason are optional for Terac, but we always send them. |
| Submission statuses | — | `screen_passed`, `screened_out`, `in_progress`, `awaiting_review`, `approved`, `rejected`, `abandoned`. Webhook `from` can also be `init` or `screening`. |
| Webhook events | subscribe to `submission.status.change` + `submission.approved` | `submission.approved` duplicates the `status.change → approved` delivery under a different `X-Event-ID`. **We subscribe to `submission.status.change` only.** |
| Webhook payload | — | `{event_type, event_id, resource_id (submission id), occurred_at, opportunity_id, from, to}`. |
| Webhook delivery | — | Timeout is **10 s**; 5xx/408/429 are retried 12 times over about 2.5 days; other 4xx are not retried; redirects are not followed. Our route acknowledges first and runs `onSubmissionAwaitingReview` in `after()`. A handler failure opens an incident `terac_webhook_handler_failed`, and the reconciler must pick it up. |
| Confirm subscription | `POST /hooks/subscriptions/{id} {}` | Confirmed. Terac POSTs a signed `webhook.ping`; anything but 2xx returns 412. The receiver therefore needs `TERAC_WEBHOOK_SECRET` **before** confirming (see `scripts/register-terac-webhooks.ts`). `target_url` must be public https; one subscription per URL (409 on duplicate). The secret can be re-read with `GET /hooks/subscriptions/{id}/secret`. |
| Callback | `?teracSubmissionId={id}&result=completed|rejected` | Confirmed. `result` may also be `screened_out` or `quota_full`; if omitted, it defaults to `completed`. `rejected` moves the submission straight to **rejected** (no `awaiting_review` webhook, so the juror is unpaid). |
| Demo redirect | — | "Run a demo redirect" in Terac's dashboard opens our page with `teracSubmissionId=demo_…`. `/api/juror/submit` answers it normally but **stores nothing**. |
| Auto-reject | — | Only when Terac enables "Redirect URLs" for an opportunity (off by default; not self-serve). In that mode, `awaiting_review` submissions without callback evidence are auto-rejected after 6 h; the sweep never approves `manual_review`. |
| Bodies | — | Every POST/PATCH needs `Content-Type: application/json` and a JSON body (`{}`); otherwise 415. An empty body returns 400 `PARSE_ERROR`. |
| Errors | — | Key-check errors (401/403/429) nest under `error`, while operation errors are flat `{code, message, issues?}`. We read both. 412 maps to `TeracPreconditionError`, 409 to `TeracConflictError`, 429 to `TeracRateLimitError` (with `retryAfterSeconds`), and everything else to `TeracError`. |
| Rate limit | 100 req/key, resets after 60 s idle | Precisely: 100 accepted requests in a row; the count resets only after **more than 60 s with no accepted request**; refused requests don't count. A 429 carries `Retry-After`. The client never retries or polls. |
| Device types | `['desktop','mobile_ios','mobile_android']` | Confirmed. Omitting the field allows desktop, mobile and `other`, but not tablets. |
| Participant PII | — | Submission endpoints return `participant_name`, `participant_email`, `participant_linkedin_url` and `participant_photo_url` unless the org hides them in Terac settings. Our client drops everything but `id`/`status`. **Recommend hiding names/emails in the Terac org settings** (principle 9). |
| Org context | `balanceDollars` | Confirmed (number). It also returns a markdown briefing with org policies for task/panel descriptions. |

## Open items needing a human

1. A `TERAC_API_KEY`, a `TERAC_PROJECT_ID` (via `GET /projects` or `POST /projects`), and ideally a **sandbox org** with its own key, from the Terac team.
2. After deploy, run `npx tsx scripts/register-terac-webhooks.ts https://<host>`, set `TERAC_WEBHOOK_SECRET`, redeploy and re-run to confirm. A sandbox org needs its own subscription and secret.
3. Ask Terac to hide participant names/emails for the org, and decide whether to request launches without a screener (`without_screener`).
4. The opportunity `title` and `description` are shown to participants. Like the panel descriptions, they must not contain the customer's product name.
